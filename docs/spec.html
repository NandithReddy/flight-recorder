Flight Recorder

An evaluation and regression harness for LLM agents. It records real agent runs, freezes them into replayable test cases, and blocks any change that quietly makes the agent worse.

The problem it exists to solve

Conventional software fails loudly. A bad deploy throws an exception, a test goes red, a page 500s. Agent software fails quietly: you change one line of a prompt or move to a newer model, and the agent keeps answering — confidently, plausibly, and 8% worse. Nothing throws. Nothing goes red. You find out from a customer, six weeks later, and by then you have shipped forty other changes and cannot tell which one did it.

The teams that solve this all converge on the same shape: capture what production actually did, turn a slice of it into a fixed test set, and re-run that set against every proposed change with an honest before-and-after. Almost nobody has built it, because it is unglamorous and because getting the measurement trustworthy is much harder than getting it to produce a number.

That gap is the whole opportunity. Producing a number is a weekend. Producing a number you would stake a release on is the project.

How the system works

Two loops. The first runs continuously in your agent's normal life and costs almost nothing: wrap the model and tool calls, emit spans, append them to a store. The second runs on demand, before a change ships: take frozen cases out of that store, replay them under the new configuration, score both sides, and compare.

The objects you will model

Get these seven right on day one and the rest of the system falls out of them. Get them wrong and you will rewrite the store twice.

Trace
One immutable recording of one agent run: input, ordered spans, final output, and totals for tokens, cost, and wall time. Never mutated after write — everything else references it by id.
Span
One step inside a trace: a model call or a tool call. Carries its parent, name, input, output, token counts, latency, and error state.
TestCase
A trace promoted into a fixture: the original input, a list of assertions, an optional judge rubric, tags, and a pointer to the baseline output it should be compared against.
RunConfig
Everything that could change the answer — model id, prompt version, tool set, temperature, seed. The unit of comparison. A report is always config A vs config B.
Attempt
One execution of one TestCase under one RunConfig. Produces a new Trace, which means attempts are themselves fully inspectable recordings.
Verdict
Pass or fail for one attempt, plus the score, the reason, which scorer produced it, and how much that scorer should be trusted. The provenance field is what lets the report separate hard failures from judged ones.
Report
An aggregate over attempts against a baseline: pass-rate delta with a confidence interval, cost delta, latency percentiles, and the per-case list of what regressed.

Components, in build order

Recorder

A thin wrapper at the client boundary that emits OpenTelemetry spans using the GenAI semantic conventions. Do not invent a span format — you get ecosystem compatibility for free and you skip a week of bikeshedding. Redact on the way in, never on the way out, so sensitive payloads never touch disk. Sample in production, but always keep 100% of runs that errored or that a user thumbed down; those are the traces you will actually want to freeze.

Store

An index plus a blob store, behind one interface. SQLite for the index and content-addressed files on disk for payloads gets you running locally in an afternoon and swaps to Postgres and S3 later without touching callers. Content-address the payloads — agent traces repeat the same system prompt thousands of times, and deduping cuts storage by an order of magnitude.

Freezer

The CLI that turns a real trace into a test case. This is the component that decides whether anyone ever uses the tool. Hand-writing fifty test cases is the reason eval tooling sits unused, so the freezer must propose assertions by reading the trace — this tool was called, this field appeared in the output, this finished in four steps and under nine cents — and let you accept, edit, or drop each one. Authoring a case should take ninety seconds, not fifteen minutes.

Replayer

Runs the matrix of cases × configs with real concurrency, rate-limit backoff, and resumability. It has two modes, and the second is the most defensible idea in the project:

  • Live replay — tools execute for real, inside a sandbox. Tests the whole system as it will actually behave.
  • Stubbed replay — tool responses are played back from the original recorded trace. The environment is held perfectly still, so the only thing that varies is the model and prompt.

Run both and the difference between them is diagnostic. If a case regresses in stubbed mode, your prompt or model got worse. If it only regresses live, the world changed underneath you — an API returned different data, a page moved, a rate limit hit. Nearly every eval tool conflates these two and leaves you guessing.

Scorer

The hard part, and the part that determines whether the numbers mean anything. Three tiers, in strict order, with early exit.

Two details in there matter more than they look. Pairwise beats absolute: asking a judge "is B better than A" is dramatically more stable than asking it to score A out of ten, and it maps directly onto the regression question you actually care about. Randomise the order of the two candidates, because judges have a well-documented position bias and an unshuffled harness will report a win for whichever side you happened to put first.

Reporter

Aggregate attempts into a diff and — this is the part that separates the project from its competitors — refuse to overstate it. Pass rate is a binary outcome over a small sample, so compute the interval by bootstrap resampling rather than reaching for a t-test. When forty cases go from 38 passing to 40 passing, the correct output is not "+5% improvement". It is "+5%, interval −4% to +13%, not significant at n=40." Print that sentence and a reviewer immediately knows you have done this before.

The report ships as a single self-contained HTML file: headline deltas at the top, then the list of regressed cases, each one expanding into a side-by-side trace diff so you can see the exact step where the two runs diverged.

Gate

A GitHub Action wrapping the CLI. It fails a pull request on any of four conditions: a statistically significant pass-rate drop, any case tagged p0 regressing at all, cost per task above a ceiling, or p95 latency above a ceiling. Baselines are pinned by commit, so the comparison is reproducible months later.

Stack

TypeScript on Node 24. Not because it is better at this, but because it is where agents are actually written — the AI SDK and MCP ecosystems live there, adoption is a single npm i, and the CI story is trivial. If your target audience is ML teams rather than product teams, build the identical design in Python with Typer and Pydantic; nothing in the architecture changes.

  • Tracing — OpenTelemetry, GenAI semantic conventions.
  • Storage — better-sqlite3 index, content-addressed blobs on disk, one interface so Postgres and S3 drop in later.
  • Isolation — Docker or Vercel Sandbox for live replay. Borrowing this costs two days; building it costs two weeks.
  • Statistics — bootstrap resampling, ~10,000 iterations. Small, dependency-free, correct.
  • Report — static self-contained HTML. No server, no dashboard, no auth.
  • Its own tests — Vitest, with real coverage. An eval tool without tests is a punchline, and reviewers check.

Build phases

The exit criteria matter more than the day counts. Each one is a thing you can demonstrate, not a feeling of doneness.

#PhaseWhat shipsDaysExit criterion
00 Spike One trace captured, stored, replayed by hand 1–2 End-to-end skeleton exists. No scoring yet.
01 Recorder SDK wrapper, OTel spans, redaction, sampling 3–5 A real agent run produces a complete, replayable trace.
02 Store + freezer Index, blob store, freeze with proposed assertions 2–3 Ten cases created from real traces in under twenty minutes.
03 Replayer Matrix runner, backoff, live and stubbed modes, sandbox 4–6 Fifty cases × three configs runs unattended to completion.
04 Scorer Three-tier ladder, pairwise judge, calibration set 5–7 κ ≥ 0.6 on 200 labelled examples; judging under 15% of run cost.
05 Reporter Bootstrap intervals, regression list, trace diff, HTML 3–4 Report refuses to call a two-case delta significant at n=40.
06 Gate Exit codes, GitHub Action, pinned baselines 2 A deliberately worsened prompt fails CI on a real pull request.
07 Dogfood + writeup Run against a real agent, publish the results 4–5 A public report showing a regression the harness caught first.
Do not cut phase 07

It is the phase everyone drops when they are tired, and it is the half that converts working code into career value. A mediocre project with an excellent postmortem beats an excellent project with a README — because the postmortem is the only artefact that demonstrates judgement rather than throughput.

Scope boundaries

Everything on the right is a reasonable idea and a separate product. Refusing them is what lets version one exist.

Version one builds

  • Local-first CLI, single command to first report
  • Live and stubbed replay modes
  • Deterministic assertions and a calibrated pairwise judge
  • Bootstrap confidence intervals on every delta
  • Self-contained HTML report with trace diffs
  • GitHub Action gate with pinned baselines

Version one refuses

  • A web dashboard, accounts, or multi-tenancy
  • A hosted service of any kind
  • Synthetic dataset generation or fine-tuning
  • Real-time production monitoring and alerting
  • Automatic prompt optimisation
  • Support for anything that is not an LLM agent

Why this is not a clone

Braintrust, LangSmith, Langfuse and Arize all occupy this space and all have funding you do not. You will not out-feature them, so do not try. Win on five specific things they are collectively weak at:

  • Stubbed replay separates model regressions from environment drift. Almost everyone conflates the two.
  • Auto-proposed assertions make authoring cases take ninety seconds, which is the entire adoption problem.
  • Published judge calibration. Everyone ships an LLM judge; nearly nobody reports how well it agrees with a human.
  • Statistical honesty. Confidence intervals and explicit non-significance, in the default report, not an advanced setting.
  • Local-first and CI-native. No account, no upload, no dashboard. It runs in a pull request and prints a verdict.

Definition of done

Not "the features are built" — these six, all checkable by someone else:

  • From npm i to a first real report in under twenty minutes, on someone else's machine.
  • The judge's agreement with human labels is published as a number, and the report degrades honestly when that number is low.
  • Stubbed and live replay produce a diagnosable difference on at least one real case.
  • Every headline delta in the report carries an interval, and small samples are labelled not significant.
  • A pull request that makes the agent worse is blocked by the gate, demonstrably, on video or in a public repository.
  • A writeup exists covering what you measured, what surprised you, and what you got wrong and corrected.
The one-week off-ramp

If three months is more than you want to commit, phases 00 through 03 plus a Tier-1-only scorer is roughly seventy hours — two weeks full time. It captures, freezes, replays and diffs on deterministic assertions alone, with no judge and no statistics.

That version already demos well and already catches real regressions. Ship it, put it in front of people, and let their reaction decide whether tiers two and three are worth the remaining six weeks.

Flight Recorder is a working name. Estimates assume an experienced engineer with AI assistance and a real agent to dogfood against; add roughly 30% if either is missing.
