Project postmortem

Wrong, Not Broken

I built a regression harness for LLM agents. It found fourteen defects. Not one of them was a crash — every single one was a number that was quietly wrong, including in the harness's own judge, which measured worse than a coin flip until I worked out I had been grading it blind against humans who held the answer key.

The premise

Conventional software fails loudly. A bad deploy throws, a test goes red, a page 500s. Agent software fails quietly: you change a line of a prompt or move to a newer model, and the agent keeps answering — fluently, confidently, and eight percent worse. Nothing throws. You find out from a customer, six weeks later, after forty other changes have shipped.

So I built the thing that catches that: record real agent runs, freeze a slice of them into replayable test cases, and re-run those cases against every proposed change with an honest before-and-after. Traces go to a transactional store; assertions are proposed automatically by reading a recording; a three-tier scorer runs cheap deterministic checks first and an LLM judge only when it has to; the report carries confidence intervals; and a CI gate blocks a merge on a significant regression.

What I did not expect was that the project would spend most of its life catching itself. Fourteen defects, across seven build phases. Every one produced a wrong number and no error. Seven of them were in the measurement apparatus — the part whose entire job is to be trustworthy — and one was caught by the finished gate, in a commit of mine that a fully green test suite had waved through.

The fourteen

Presented in the order they were found, because the order is part of the argument: the later ones were found by the tool, using the earlier ones.

01

Every model call was recorded twice

The client handed to an agent arrives already instrumented. An agent that wants a differently-scoped client naturally calls wrapModel again — and each call then recorded two spans, doubling every token count and every cost total.

Caught by: a span count of 10 where the test expected 7. No error, no symptom, just wrong totals.
02

A trace mutated after it was stored

The sampling decision was attached to the trace object with Object.assign, after the trace had been written. Traces are content-addressed, so the same trace now hashed differently depending on whether you hashed it before or after the call returned — meaning one id could acquire two hashes.

Caught by: a round-trip test asserting the stored trace equalled the returned one.
03

The assertion proposer would have certified a hallucination

Asked for quarterly growth, a 3B model skipped the lookup entirely, called the calculator with 450 and 500 — figures it invented — and answered "11.11%". Arithmetically correct, wholly fabricated. And because 11.11 genuinely appeared in a tool's output, the proposer would have pinned it as a verified fact.

Verification now follows provenance: a tool's output is evidence only if the tool's own inputs were themselves grounded. Otherwise the tool faithfully computes over invented numbers and launders a hallucination into an apparently checked fact.

Caught by: pointing the harness at a real model for the first time. Invisible against the scripted mock.
04

The step diff explained nothing

It compared spans by name. On a report comparing two models, every step therefore "differed" — for the trivial reason that the model is the change. It printed "the baseline called qwen2.5:7b, the candidate called llama3.2:3b" twenty-five times.

It now compares decisions — which tools a step asked for — not identities. The same report then says, unprompted and across twenty of twenty-five diffs: "The runs diverge immediately: the baseline asked for search, the candidate asked for calculate." That one sentence is the smaller model's entire failure mode.

Caught by: reading the output of a real run instead of a test fixture.
05

I compared two things that were not comparable

I recorded in the project's own decision log that a weakened prompt "barely touches" the stronger model, citing 83% against 82%. Those were different configurations — one of them a temperature variant, not the baseline at all.

The real comparison is a 20% drop in case pass rate (−36.7% to −6.7%, significant at n=30) and p95 latency going from 9.5s to 50s. The assertion average hid it completely: 132 of 159 assertions still pass, because a case passes only if every hard assertion holds.

Caught by: running the gate. The tool disagreed with its author.
06

Half the calibration set was free points

28 of the first 49 comparison pairs had a blank side, because that run had errored. "An answer beats no answer" is obvious to a human and equally obvious to a judge, so those pairs would have burned a person's attention and inflated the agreement score — human and judge concurring perfectly for reasons unrelated to judging.

Caught by: labelling them by hand and noticing the second pair was empty.
07

The judge was worse than a coin flip

Measured against 47 human labels: κ = −0.102, interval (−0.203, −0.008). The interval excludes zero, so that is a measurement rather than noise. Its own section below.

Caught by: the calibration tier, which exists for exactly this.
08

Each calibration destroyed the previous one

Calibration results were keyed by label set alone, so running a second one overwrote the first — the number you most want to compare against. A calibration is a comparison; storing only the latest makes the comparison impossible.

Caught by: running three in a row and watching the evidence vanish.
09

The gate caught me shipping the regression it was built for

A git checkout carried an uncommitted prompt edit across a branch boundary, and a commit titled "Pin the mock in tests that are not about prompts" silently deleted the instruction telling the agent to verify its figures. Every test passed. Typecheck passed. The agent stopped verifying its numbers.

The gate failed the push, comparing the agent as it stood against the baseline recordings committed to git: pass rate −100%. I kept both commits in history rather than amending them away — the only defect on this list that nobody staged.

Caught by: the finished gate, on this repository, by accident.
10

Stubbed replay served a recorded failure as a success

The stub replayed only a span's output, ignoring its error. A tool call that failed on the baseline replayed as a successful null — which LangChain stringifies into a tool message reading "null" with success status. The candidate saw "null" where the live run saw the error text, the conversations silently diverged, and the report still said identical: true.

The defect sat unreachable for four phases: the hand-rolled loop aborts on tool errors, so an errored span never appeared in a clean baseline. LangGraph's loop recovers from tool errors — and recovering is exactly what produces a freezable trace containing a failure. The recording of a failure is still a recording of the environment; the stub now rethrows it.

Caught by: adversarially reviewing the foreign-agent integration.
11

The temperature axis was dead — and its ghost was in my own decision log

Both example agents hardcoded temperature: 0 in their model calls. A matrix config saying qwen2.5:7b@0.9 changed the config's identity and nothing else; every request carried 0. The "41 identical pairs" the calibration pool reported were identical because the 0.9 runs were the 0 runs, byte for byte — and an earlier correction in my decision log confidently attributed a miscompared figure to "temperature 0.9", an axis that did not exist.

Third instance of the same failure class this project has caught — model, then prompt, then temperature, each hardcoded somewhere a config was supposed to reach.

Caught by: the same adversarial review. The fix is pinned by a test per agent.
12

The matrix reported a pass rate over whichever cells happened to run that day

The runner hands every finished cell back to the caller, but a resumed cell — one whose result was already stored — arrived carrying its attempt row and no trace. The summary skipped cells without a trace. So on any run after the first, the printed rate covered only the cells that had not already finished: a 120-cell matrix announcing 23/32.

I published one of those. The "64% under the hand-rolled loop" in the table below started as a rate over a fraction of a suite, selected by which cells were unfinished that afternoon, and it reached three documents before anyone tried to re-derive it. The comparison is now a committed script rather than a console line copied into prose.

Caught by: trying to reproduce my own published number and getting a different one.
13

An outage was cached as an agent failure, and it inverted a finding

Twenty-three of the hundred and twenty cells in the metrics suite had died with No Ollama daemon at 127.0.0.1:11434. The model host had been killed mid-run, weeks earlier, when a session was interrupted. Each of those runs was stored as a completed attempt, resumed by every matrix run since, and counted in every rate computed from that suite. They are not evidence about an agent; they are evidence that a laptop process was not running.

The damage was not hypothetical, because I was in the middle of correcting defect 12 when I found it. With the outage runs in, the loop comparison read "the strong model gains fourteen points under ReAct". With them purged and the twenty-three cells genuinely re-run, the strong model gains nothing — 97% under both loops. The correction I had just written was itself wrong, in the more flattering direction.

Recording the failure is right; a trace of a failed run is still a trace. Treating the harness could not run the agent as the agent failed is what was wrong. Provider adapters already name these errors, so the matrix now recognises them, retries, reports the cell as one that could not run, and stores nothing — so the next run re-runs it instead of serving the outage forever.

Caught by: reading the error messages behind a corrected number instead of the totals.
14

The merge gate reported PASS when it had compared nothing

A config spec is model#prompt. Write --baseline v1 and v1 parses as a model name, nothing matches it, and the comparison runs over zero cases — at which point the pass-rate delta is NaN, "not significant" is trivially true, every check passes, and the build goes green. A typo in a CI argument was indistinguishable from a clean bill of health.

The statistical report had guarded this for months: with no data it prints an explainer instead of a row of NaN. The gate — the half that actually decides whether code ships — was the half that stayed quiet. A merge gate whose failure mode is silent approval is worse than no gate, because it is trusted. It now exits non-zero and prints the parsed config ids next to the specs you gave it.

Found by an adversarial review of the two corrections above, which also found that both of those were themselves incomplete: the bucketing fix had left temperature out of the key, and the outage fix was applied when writing an attempt but never when reading one, so every outage already sitting in a store was still being served. The corrections needed correcting.

Caught by: review agents pointed at my own fixes, with instructions to refute their findings before reporting them.

The agent I didn't write

Everything above was measured on an agent I built as a fixture, which is the weakest possible subject — a harness that has only ever tested its author's own loop has proven very little. So the final phase points it at LangGraph's prebuilt ReAct agent: the most widely deployed open-source agent loop in the JS ecosystem, whose decisions about tool routing, retries and stopping are not mine.

The integration is a single ~150-line bridge — a chat model whose generate method delegates to the harness's own client — plus one registration line. Recording, stubbed replay, the freezer, the matrix and the gate all applied unchanged, which was the promise of the seams and is now a tested claim rather than an intention. The whole foreign loop also runs against the deterministic mock, so CI exercises it with no model and no network.

And the comparison it enables produced the finding I would least have predicted — after two corrections, one of which reversed half of it. Same thirty tasks, same tools, same prompts, same temperature; only the loop differs. Both loops are scored against a single assertion set, because each suite was frozen from its own baseline and comparing their own rates would compare two rulers as well as two loops:

llama3.2:3b — hard assertions60%71%

qwen2.5:7b — hard assertions97%97%
qwen2.5:7b — cases passed27 / 3027 / 30

The weak model gains eleven points and stops dying entirely. The strong model cannot tell the two loops apart. Both loops provoke the same thirteen failed tool calls from the small model — the mistakes belong to the model, not the harness around it — but LangGraph's ToolNode catches each error and hands the text back for a retry, where my loop lets it abort. Thirteen dead runs become none. The 7B model, which gets its arguments right, never reaches the retry machinery at all: 97% either way, the same twenty-seven cases.

So the loop is not a quality parameter in general. It is a recovery parameter, and it pays in exact proportion to how often the model errs — which is a narrower claim than "ReAct is better", and the one the data supports. It also predicts where the difference should show up and where it should not, which is what makes it worth publishing at all.

The caveat, since the comparison flatters the loop I did not write: the tasks and the tools are mine, so this measures how two loops handle my tools' errors rather than making a general claim about LangGraph. What transfers is the method — hold the model, prompt, tools and temperature still, vary the loop, score both against one ruler — not the eleven points.

The judge that preferred hallucinations

The third tier of the scorer exists to answer one question: how much is the judge's opinion worth? You take pairs of answers a person has labelled blind, run the judge over them, and compute Cohen's κ — agreement corrected for chance.

Raw agreement is a flattering and near-meaningless number. If seventy percent of pairs are ties and the judge always says "tie", it agrees seventy percent of the time while knowing nothing. κ scores that at zero.

My first judge scored below zero.

Why it failed

The confusion matrix said where, and the judge's own stated reasons said why:

"Answer B provides supporting details that confirm the…" — preferring the run that invented 450 and 500.

"Answer B provides a calculation supporting the figure" — preferring fabricated working.

"Answer A shows the calculation, while Answer B only states…" — preferring the run that printed a tool call as prose and computed nothing at all.

The judge was rewarding the appearance of work. Models that fabricate produce more text, more visible arithmetic, more apparent rigour — and the judge read all of that as quality. So it preferred hallucinations, systematically, and would have done so silently forever.

Part of the blame is mine. The prompt said to judge whether an answer was "correct, complete and supported by the work shown". A fabricated calculation satisfies "work shown" perfectly. I had written an instruction that rewarded the exact behaviour it was meant to detect.

The other half of the failure only surfaced because of a decision that felt like a waste of time while making it. Roughly half the comparison pairs were the same model under two prompts, usually producing the same correct answer — dull to label, and I nearly filtered them out. The judge said TIE zero times in 47 pairs. I said it twenty-one times. It could not express equivalence at all; it always invented a winner. Only the "boring" pairs could have shown that.

What fixed it, and what did not

A rewritten prompt — one that explicitly states that shown arithmetic can be invented, that length is not accuracy, that an admission of ignorance beats a plausible fabrication, and that TIE is a real verdict — moved κ from −0.102 to 0.209. Above chance, and nowhere near good enough.

A bigger model did not help. llama3.1:8b under the same instructions scored 0.089, with an interval crossing zero. The prompt mattered more than the model, which is not what I would have guessed before measuring.

What eventually worked was giving up on describing what I wanted and specifying a procedure instead. v2 told the judge that TIE was a real verdict; it still called 11 of 21 equivalent pairs a win for one side. v3 stopped asking for an opinion: extract the final figure from each answer, compare those two figures, and if they match the verdict is TIE — stop, do not look for a tiebreaker. Ties went from 9 correct to 19, and κ from 0.209 to 0.459.

Telling a model what to conclude is a hint. Telling it what to compare is an instruction. That is the most portable thing I learned here.

The unfair test I had been running

Then I read my own answer key, which opens with a line I had written months earlier and never thought about again:

"Keep this open while labelling. Knowing the correct answer is what makes a label worth anything."

Every one of those 47 human labels was made by someone holding ground truth. The judge being measured against them saw two anonymous strings and no data. Asked which of "18.33%" and "11.11%" is correct, with no tools and no reference, its best available strategy is a coin flip — and κ had been faithfully measuring one. I had spent four prompt versions trying to fix a judge that was mostly being asked to guess.

So I gave it the same key. κ fell to 0.188.

The confusion matrix explains it in one line each way. On pairs that genuinely differ, the rubric made the judge nearly perfect — 22 of 23, against 11 of 23 blind. On pairs that agree, its ties collapsed from 19 of 21 to one. Handed a reference, the model stops comparing the two answers and starts grading each one's resemblance to the reference, so the answer that also shows the derivation beats the answer that merely states the same correct figure.

That is the "detail is quality" failure from v1, walking back in through the door my fix had opened.

v4 is v3 with one paragraph added — the rubric is explicitly out of scope until after the tie test, in capitals, because the instruction that most needs to survive is the one the model is most motivated to skip. 0.188 → 0.687.

The number I finally hit, with an asterisk

My own spec set the bar at κ ≥ 0.6 on 200 labelled examples. The judge now scores 0.687, and the same prompt reaches 0.654 on a different model, so this is a property of the instructions rather than a lucky draw.

Three reasons I am calling that provisional rather than done:

  • The 95% interval is (0.474, 0.865). At n = 47 the point estimate clears 0.6; the interval does not, so I cannot yet claim the true value does.
  • The spec said 200 labels. I have 47.
  • v3 and v4 were written against the same 47 labels they are scored on. That is tuning on the test set. A prompt fitted to a confusion matrix can fit that matrix's noise as easily as its signal, and nothing I have distinguishes the two yet.

All three close with the same action, which is the next thing I would do: label a fresh set and treat it as held-out validation rather than more training data. If it comes back under 0.6, v4 is overfitted and the honest headline reverts — an outcome worth having measured either way.

For most of this project's life the honest answer was "I did not hit my own number, and here is exactly how far off I was." The tier existed to make that statement possible, and the machinery that marked those verdicts untrusted is the same machinery now letting them through. That is only safe because the threshold is a measured quantity rather than a hopeful one — which is the entire argument for building the third tier at all.

Things that were true and surprising

The 8B model failed nearly nine runs in ten as an agent, and was the weakest of the three as a judge — until the prompt was fixed, at which point it landed within 0.03 of the 7B model. Parameter count predicted neither the agent failures nor the judging, and the arrows in that last column are all prompt, not model.

Broken agents are cheaper and faster

This is the finding I would put in front of anyone optimising an agent on cost. A model that skips its lookup and fabricates a number does less work: fewer model calls, fewer tool calls, fewer tokens, lower latency. In this project's own numbers, the fabricating configuration was 4.6× faster and used half the tokens.

Every resource metric prefers it. Only a semantic check catches it. That is the whole argument for reporting quality, cost and latency in one view and never separately.

An aggregate hid a fifth of the suite

A weakened prompt left 132 of 159 assertions passing — 83%, which reads like nothing at all. At case level, where a case passes only if every hard assertion holds, it was a 20% drop and statistically significant. Averages are where regressions go to hide.

What I would do differently

  • Point it at a real model on day one. A deterministic mock is a fast way to build a harness that only works against a deterministic mock. Three of the fourteen were invisible until a real model was involved, and they surfaced within minutes of one being connected.
  • Write the judge's prompt against a confusion matrix, not from intuition. My intuition produced a judge that was worse than random. Four versions, each written against its predecessor's matrix, produced one at 0.687.
  • Specify a procedure, not a preference. Telling the judge "TIE is a real verdict" changed almost nothing. Telling it to extract both figures and compare those moved κ by 0.25.
  • Check that the grader and the graded have the same information. I spent four prompt versions on a judge that was, for half its task, being asked to guess — because the humans it was scored against had an answer key open and it did not.
  • Treat every prompt as configuration. The agent's prompt, and the judge's. Both change the answer, so both belong in the comparison matrix and in version control. I had the agent's prompt as a config field and ignored it for four phases.
  • Keep the boring test cases. The pairs that felt like filler are the ones that caught the judge's inability to say "equal".

What I would still not claim

The judge's 0.687 is measured on the same 47 labels that two of its four prompt versions were written against — tuning on the test set, and provisional until it is checked on unseen pairs. The task set is synthetic — thirty questions over a fictional metrics warehouse — chosen so ground truth is always derivable, at the cost of realism. And the "foreign" agent shares my tools and prompts by design, so the comparison isolates the loop; a fully alien agent with its own tools would need the recording proxy this architecture deliberately avoided. Each of these is a boundary I would state in a review, so it belongs here too.

What it cost

Nothing, in money. The whole project runs on local models through Ollama — no API key at any point, including the calibration. That was a constraint I was handed rather than one I chose, and it made the project better: it forced a second provider adapter, which is what proved the provider abstraction was real, and it made "local versus hosted" a genuine axis of comparison rather than a hypothetical one.

The expensive input was attention. Forty-seven pairs, labelled by hand, roughly twenty minutes. That is the only part of this that cannot be automated, and it is the part everything else is measured against. If a model labels the calibration set, the judge has been graded by a model — which is precisely the failure the calibration exists to detect.

211 tests, all seven build phases complete; the gate demonstration is a public pull request blocked by CI with every unit test green. Traces are stored transactionally with payload-level deduplication; assertions are proposed from recordings and reviewed rather than authored; reports carry percentile bootstrap intervals over paired resamples and refuse to name a direction they cannot support. Every figure in this piece is reproducible from the repository.
